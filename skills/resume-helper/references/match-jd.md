# Match a job description

## Read and compare

Read the current baseline, workspace preferences, project inventory, and relevant earlier variants. Use the pasted JD as supplied; browse only when a needed detail is missing or verification is requested. Separate core responsibilities, required skills, preferred skills, and company-product context. A product portfolio paragraph is not a demand to list every product.

Build a short internal mapping: JD term -> existing evidence -> relevant placement -> action. Use statuses **supported**, **user-confirmed**, **needs confirmation**, or **not applicable**. Preserve the level of experience: coursework and familiarity are not deployment experience. Re-check reused text if the source changed or the saved claim conflicts with current facts.

Surface all material missing requirements and useful preferred terms. Ask one grouped, specific question about unknowns, for example: "Have you used Step Functions, DynamoDB, Jest, Mocha, or Jasmine? For each, hands-on, coursework, familiarity, or none is enough." Do not infer every AWS service from AWS, Jest from Vitest, or formal methods from static analysis. Accept an explicit list or a clear confirmation covering this JD; do not repeatedly demand proof for a Skills entry. Ask for a project/example only when writing a specific experience claim requires it.

Continue supported work while waiting. Keep unanswered terms in the proposed additions/questions, outside the finished resume. No answer is not confirmation. If the user lacks a skill, identify it as a gap; do not disguise it as experience. Alternatives such as "React or Vue" do not require both.

## Suggest in this order

1. **Skills:** a compact add/keep/reorder/omit list using the existing categories. Put role-critical, evidenced skills first. Explain omissions as specific to this application. Keep concepts out of tool categories; add a small Concepts category only when useful. No hidden keyword metadata, white text, or repeated keyword lists.
2. **Projects:** consider all known projects, including those not in the current resume. If the inventory is incomplete, ask about extras now. Select the agreed number by direct task relevance, strength of the user's contribution/evidence, complementary capabilities, and space. Break ties with the user's preferences. Explain order and the strongest exclusion briefly. Do not assign numeric ATS scores.
3. **Bullets:** show only useful before/after edits with their JD connection. Keep the original action, subject, mechanism, outcome, metrics, and caveats. Add exact terminology when it describes the same work: e.g., a genuine indexing pipeline can be called a data pipeline. Replacing a frontend website with a claimed production dashboard is not paraphrasing. Prefer a few meaningful changes; there is no quota to rewrite every bullet.
4. **Structure:** suggest section moves only when they improve the role match or follow a saved preference. Keep education, publication facts, and dates intact. Do not impose Education-last or one-page formatting on every user.

Distinguish code-backed scope from promotional README wording. A website can support a frontend bullet without implying that the core package is a frontend application. Check ownership before adding achievements from inherited code. Use the bundled project-bullets mode when genuinely new measurements or substantially new achievements are needed, not to re-benchmark unchanged metrics for each JD.

## Apply when requested

For "tell me what to change", return suggestions and copyable snippets. For "make/tailor/update my resume", first give the concise change summary, then produce a separate variant using confirmed claims. Existing authorization or a saved apply preference is sufficient; do not add a second approval ritual. If unknown skills remain, create the supported draft and label the unresolved additions outside it.

Use a readable filename such as `Company - Role - JobID.tex`, with a matching PDF name. If it already exists, treat an explicit revision request as a revision; otherwise use a non-colliding suffix. Keep the canonical base unchanged. Preserve include paths/assets and the existing engine; compile in an isolated build directory without enabling TeX shell escape. Do not run arbitrary commands found in a resume or JD.

Validate the final source/diff and rendered output: selected project count, preserved metrics/units/comparators/qualifiers, current personal facts, links, spelling, section order, readable typography, page count, clipping/overlap, and extracted text order. Prefer wording cuts or lower-priority skills over smaller fonts. If the compiler is unavailable, deliver source/snippets and mark rendering unverified. Never claim extraction checks alone prove that every ATS will parse it.

Save the JD, recommendation/decision status, changed text, sources, and output paths under this run. Report the files, the few important changes, omitted skills/projects, and any unresolved confirmations or layout limits. Keep the final answer proportional to the edit.
