# Workflows

## Setup

1. Use a user-selected tracker directory outside the installed skill or public repository. If none is specified, offer `job-tracker` in the current workspace. Inspect existing instructions/files before initializing; do not overwrite a previous tracker.
2. Run the setup helper documented in [tracking.md](tracking.md). It copies a blank `me.md`, the source seed and empty lists, and installs local command wrappers for the chosen host. Existing files are preserved. Review reported command conflicts instead of overwriting them.
3. Ask one concise group of questions: career stage/experience, jobs or internships or both, desired/avoided roles, India location/availability, salary basis and flexibility, company tolerance, and local resume path. All fields are optional. Tell the user they can edit `me.md` themselves later. Their answers to these setup questions may be recorded when you explicitly say they are for filling `me.md`. Do not block public research on optional unanswered fields.
4. Inspect the host's actual available web/browser/connectors. Test read access rather than assuming plugin installation means signed in. Ask the user to sign in to their chosen LinkedIn, Naukri, Wellfound, Indeed and Telegram services in their own browser where needed. They need not connect every service to start. Report each as available, sign-in needed, unsupported or untested. Do not claim that browser sign-in makes an unrelated API authenticated.
5. Telegram public previews can work without login. If previews are incomplete, offer the available signed-in browser or a user-configured API integration. This package does not bundle an API login client. A separate API client must use local user-operated sign-in, secure credential/session storage outside the tracker, and only allowlisted channels. No secrets in chat or source control. Respect Telegram content-use restrictions; authentication is not permission to redistribute channel archives or use them for training.
6. Populate only confirmed profile facts. Keep the starter registry labelled untested on this installation; a URL is not proof of access, current hiring or employer-wide coverage. Explain the four commands and report setup/access gaps briefly. Do not start scheduled scans.

## Scrap

1. Read `me.md`, `source.md`, both lists and `.job-tracker/` evidence/checkpoints. Resume an interrupted requested scan when appropriate; a new later scan should collect new heads while retaining the old backlog. Choose jobs/internships from the profile. Create a run checklist with every active source, requested role families and region scope. Mark intentionally out-of-scope sources with reasons, not as scanned.
2. Telegram first: read all accessible messages through the prior checkpoint with overlap for edits; establish/resume an unfinished history baseline without a date cap. To avoid one channel starving the rest, fetch fresh heads across every channel first, then history. Retain channel/message IDs, full relevant message meaning, hidden/button links, media-review needs and pagination cursors. Review bundled jobs separately; classify promotions, shortlinks and forms. Do not advance a reviewed cursor until every job/link/media item is resolved or explicitly pending. Do not treat a landing page or a latest-message preview as complete history.
3. Visit every registered company portal and employer-linked ATS. Prefer available public feeds/APIs, otherwise rendered job search. Establish the board's employer identity before attribution. Follow pagination/load-more, inspect alternate campus/subsidiary boards and reconcile reported totals. Workday ceilings, repeated pages, changed totals and geographic facets can make inventories partial. Use relevant India/remote filters without excluding ambiguous locations silently.
4. Review publisher articles and their archive/feed pagination, all selected job boards, and supplementary sources. Include LinkedIn Easy Apply and employer-linked postings. Public search-engine/guest results supplement, but do not establish signed-in board coverage. Check applicable seniority/role families; a single software-engineer query is not exhaustive. Search job-alert email only if opted in. No WhatsApp scanning by default.
5. Follow job links to employer descriptions. Decode ordinary shortlinks, retain provenance and deduplicate mirrors. Forms are not automatically fake; establish employer provenance without submitting. Exclude a newly discovered role only when evidence establishes a mismatch, closure or a profile rule. Unknown startup quality/pay should be retained as pending evidence when the user's filter requires it, not labelled fraudulent or unstable.
6. Add worthwhile roles with requirements, fit components, employer/pay reasoning, source and availability evidence in local audit records. If the exact apply link cannot be established, explicitly use `Source alert - exact apply link unverified` or `Career portal - exact role unverified` **in that row**, never a misleading `Apply` label. Prefer an accessible helpful source link over an invented URL. Unknown resume fit stays `Unscored*`; known profile facts may support a provisional score. Old possibly-open discoveries may be added under this run's discovery time; no employer-announcement-date research is needed.
7. Merge new-only dated sections, preserve existing rows, validate file structure and reconcile counts. Report additions and specific remaining coverage. If work is interrupted, save next source/page/message/lead and the reason; never imply the host will keep researching after the turn ends.

## Validate

Read every existing row in the requested scope (all rows by default, including struck rows). Inspect the exact employer requisition and application availability, or a reliably attributable authoritative notice. Preserve Applied marks even for closed entries.

- **Confirmed closed:** the exact employer job/application page explicitly says applications are closed, filled, expired or no longer accepted; or a verified employer deadline unambiguously ended in its stated timezone with no extension. Save URL, observed time and short supporting evidence. Strike all five cells using the helper, leaving the hyperlink and checkbox value recoverable.
- **Open:** the same requisition is accepting applications. Reopen an earlier struck row only with affirmative evidence; do not create a new discovery entry. Seeing an Apply button is useful but an error/closed message on its destination overrides it. Do not submit or enter application data to test it.
- **Uncertain:** errors, CAPTCHA, login walls, empty search results, generic redirects, 404/410 without a role-specific closure message, snippets or uncertain deadlines. Keep the row unchanged, record uncertainty and a helpful alternate source. Never mark these closed just to tidy the list.

Do not remove a previously listed role because preferences changed; record a mismatch in audit and report it. End with numbers checked, closed, reopened and uncertain. This is the only routine command that rechecks old vacancies.

## Repair

Test every source in scope, including unresolved/retired entries when requested. Test real job/message results and pagination, not only HTTP status or homepages. Compare domain/employer/channel identity and guard against redirects to unrelated content.

For broken employer routes, find the employer-linked ATS, campus page, feed or rendered search through legitimate public navigation. Preserve the company and put still-unreachable routes in `Inaccessible or unresolved companies`, with tested alternatives and reasons. An explicit denial is not permission to try another transport to circumvent it.

For publishers, boards and channels, distinguish temporary access errors from demonstrably abandoned, irrelevant, scam-heavy or unusable sources. Try reasonable allowed alternatives. Retire persistently bad sources from the active registry only with recorded evidence; keep their URL, reason and date in `Retired sources`. A CAPTCHA or transient timeout alone does not justify retirement. Do not delete historic evidence or job rows.

Find additional relevant Telegram channels, job-alert publishers, boards and employer pages using web search, links from established sources and employer cross-links. Inspect actual recent software/India content, provenance, duplicate syndication and access before adding. Prioritize sources suitable for the user's experience; the starter Telegram list is fresher-heavy. New entries remain untested/partial until checked. Deduplicate handles case-insensitively and normalize URL tracking parameters.

Record source state, attempted routes, access time, inventory vs review completeness and continuation needs. Report added/repaired/retired/unresolved counts. Source repair alone must not be called a job scan.
